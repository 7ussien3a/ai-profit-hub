## 37. Repository-Specific Safety and Quality Guardrails

These guardrails supplement the rules above. They do not create another activation command or a second approval step.

- Resolve the current local HEAD and `origin/main` at the start of every GO cycle. Never rely on a hardcoded baseline commit from an older task or report.
- Inspect the working tree before editing, preserve unrelated user changes, and keep each commit limited to the verified GO-cycle scope.
- Use the repository's established validation path, including `python scripts/content_pipeline.py publish-check`, `python scripts/site_audit.py`, `python scripts/editorial_audit.py`, and the relevant source validator. Inspect the current command interfaces before execution.
- Do not use a wrapper that suppresses errors, stages the entire repository with `git add .`, or pushes before the scoped diff and validation results have been reviewed.
- Treat `data/editorial-decisions.json` as the current page-level indexability decision registry. Do not restore an archived or noindex page to the indexable set until that page has received individual source review, substantial editorial remediation when needed, and a matching registry update.
- Do not impose a universal word-count minimum. Judge completeness against search intent, evidence, originality, and reader utility.
- For current or date-sensitive claims, record the source publication date and verify the claim against the primary source. Treat HTTP 401, 403, and 429 responses as access-controlled or rate-limited evidence, not automatic proof that a source is dead; verify through a browser or another authoritative source.
- Run `git diff --check` and validate changed JSON, XML, JSON-LD, links, redirects, canonicals, and local images. Perform desktop and mobile browser checks for every changed public template or page.
- After deployment, verify the exact HTTPS production route, canonical URL, indexability, referenced assets, and affected discovery files. Do not infer production success from a successful push alone.
- Verify credential protection using non-secret boolean checks only. Never print credential contents, fingerprints, hashes, tokens, or private metadata.
- Prefer idempotent remediation. When a repair script is expected to be repeatable, a second validation run must not create additional changes.
- Keep this file as the sole master content-operation prompt. Do not copy its activation rules or full sections into another repository file, and do not create scheduled or background execution for it.
